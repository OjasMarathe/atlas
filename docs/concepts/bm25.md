# BM25 Ranking

**Area:** Search engine  ·  **Phase:** 3  ·  **Status:** flagship exemplar

## TL;DR

BM25 ("Best Matching 25") scores how relevant a document is to a query. For each query term
it rewards documents where the term is frequent (with diminishing returns) and rare across
the corpus (informative), while penalizing long documents that rack up term counts just by
being long. It's the default lexical ranker in Elasticsearch/Lucene and what Atlas uses for
keyword search before we add semantic re-ranking.

## The problem it solves

We need to order matching documents by relevance, not just find them. Two weaker approaches
motivate BM25:

- **Raw term frequency (TF):** "count how often the query words appear." Fails because (a) a
  word appearing 100× isn't 100× more relevant than appearing once, and (b) long documents
  win unfairly just by being long.
- **TF-IDF:** weights TF by inverse document frequency so rare words matter more. Better, but
  its TF term grows without bound and its length handling is crude.

BM25 fixes both with **term-frequency saturation** and **document-length normalization**,
each controlled by a tunable knob.

## How it works

For a query `Q` and document `D`, sum a per-term score over the query terms:

```
                             f(t,D) · (k1 + 1)
score(D,Q) =  Σ   IDF(t) · ─────────────────────────────────────
             t∈Q            f(t,D) + k1 · (1 − b + b · |D|/avgdl)
```

Where:
- `f(t,D)` — how many times term `t` occurs in `D` (from the posting list).
- `|D|` — length of `D` in tokens; `avgdl` — average document length in the corpus.
- `IDF(t)` — inverse document frequency (below).
- `k1` — **saturation** knob (typ. **1.2–2.0**). Controls how fast extra occurrences stop
  helping. As `f→∞`, the TF factor approaches `k1+1` — a ceiling. Small `k1` saturates fast.
- `b` — **length normalization** knob (typ. **0.75**), in `[0,1]`. `b=1` fully normalizes by
  length; `b=0` ignores length entirely.

**IDF** (the Robertson/Lucene form, smoothed and always non-negative):

```
IDF(t) = ln( 1 + (N − n(t) + 0.5) / (n(t) + 0.5) )
```

`N` = total docs, `n(t)` = docs containing `t`. Rare terms → high IDF; a term in every doc →
IDF near 0.

### Why the two knobs matter (the whole point)

- **Saturation (k1):** the TF factor is `f·(k1+1) / (f + k1·…)` — a concave curve that rises
  then flattens. Going from 1→2 occurrences boosts a lot; 50→51 barely moves. Matches
  intuition: presence and moderate frequency signal relevance; obsessive repetition doesn't.
- **Length normalization (b):** the `(1 − b + b·|D|/avgdl)` factor inflates the denominator
  for documents longer than average, shrinking their scores. Without it, a 10,000-word page
  outranks a tight, on-point paragraph just by accumulating incidental term hits.

### Worked example

Corpus: `N = 1,000,000` docs, `avgdl = 500`. Query term `t` appears in `n(t) = 1,000` docs,
`k1 = 1.5`, `b = 0.75`.

`IDF(t) = ln(1 + (1,000,000 − 1,000 + 0.5)/(1,000 + 0.5)) = ln(1 + ~999) ≈ 6.9`.

Doc A: `|D| = 250` (short), `f(t,A) = 3`. Length factor `= 1 − 0.75 + 0.75·(250/500) = 0.625`.
TF term `= 3·2.5 / (3 + 1.5·0.625) = 7.5 / 3.94 ≈ 1.90`. Contribution `≈ 6.9 · 1.90 ≈ 13.1`.

Doc B: `|D| = 2000` (long), `f(t,B) = 6`. Length factor `= 1 − 0.75 + 0.75·(2000/500) = 3.25`.
TF term `= 6·2.5 / (6 + 1.5·3.25) = 15 / 10.875 ≈ 1.38`. Contribution `≈ 6.9 · 1.38 ≈ 9.5`.

Doc A wins **despite half the term count**, because it's short and focused — exactly the
behavior we want.

## Our implementation in Atlas

- Lives in `src/search/ranker.{h,cpp}`, scoring over posting lists from
  `src/search/inverted_index.*`.
- **Precompute once (and maintain incrementally):** `N`, `avgdl`, a per-document length table
  `docLen[docId]`, and per-term `n(t)` (posting-list length) so `IDF(t)` is a cheap lookup.
- **Query time:** for each query term, walk its posting list of `(docId, f(t,D))`; accumulate
  the per-term score into a `docId → score` map; then take global top-K via a min-heap of
  size K.
- Params default to `k1 = 1.5`, `b = 0.75`; kept configurable so we can tune on our corpus.

```cpp
double Ranker::score(DocId d, const std::vector<TermId>& q) const {
    double s = 0.0;
    const double len_norm = 1.0 - b_ + b_ * (docLen_[d] / avgdl_);
    for (TermId t : q) {
        int f = index_.tf(t, d);            // 0 if term absent in d
        if (f == 0) continue;
        double idf = idf_[t];               // precomputed
        s += idf * (f * (k1_ + 1.0)) / (f + k1_ * len_norm);
    }
    return s;
}
```

In the **distributed** setting (Phase 4) each shard computes BM25 over *its* documents and
returns local top-K; the coordinator merges. Caveat: `N`, `avgdl`, and `n(t)` are
corpus-global statistics — if each shard uses only its local stats, scores aren't directly
comparable across shards. For M1 we accept this approximation (documented); the proper fix is
to share global term stats or use a small global-stats service.

## Complexity & trade-offs

- **Query:** `O(Σ_t |postings(t)|)` — linear in the total length of the matched posting
  lists, plus `O(matches · log K)` for the top-K heap.
- **Space:** the inverted index dominates; ranking adds only the `docLen` table (`O(N)`) and
  per-term IDF (`O(#terms)`).
- Cheap, well-understood, no training data. Ceiling: it's purely lexical — it can't match
  "car" to "automobile." That's exactly what Phase 5's semantic/hybrid ranking adds.

## Failure modes & edge cases

- **Stale statistics:** `avgdl`/`N`/`n(t)` drift as we index incrementally; recompute or
  update them, or scores slowly skew.
- **Cross-shard incomparability:** local-only IDF makes shard scores inconsistent (see above).
- **Very short docs / titles:** length normalization can over-boost tiny docs; some systems
  add a floor.
- **Non-negative IDF:** the smoothed form avoids negative IDF for near-ubiquitous terms
  (classic BM25 could go negative) — we use the `ln(1 + …)` variant.

## Alternatives we considered

- **TF-IDF** — simpler but unbounded TF and weak length handling; BM25 is strictly better for
  ranking.
- **Query-likelihood / Dirichlet-smoothed LM** — competitive probabilistic alternative;
  comparable quality, less ubiquitous tooling.
- **BM25F** — field-weighted BM25 (title vs body). A natural upgrade once we index fields.
- **Learned / dense retrieval (DPR, ColBERT)** — higher ceiling, needs models + vectors;
  that's Phase 5, layered *on top* of BM25 as hybrid ranking, not instead of it.

## Interview Q&A

**Q: BM25 vs TF-IDF?** BM25 adds tunable TF saturation (`k1`) so repeated terms have
diminishing returns, and explicit length normalization (`b`); TF-IDF has neither.

**Q: What do `k1` and `b` do?** `k1` controls how quickly extra occurrences stop adding
score; `b` controls how strongly long documents are penalized (`0`=not at all, `1`=fully).

**Q: Why can a document with fewer term occurrences outrank one with more?** Length
normalization — a short focused doc beats a long one whose higher raw count is just a
byproduct of length (see the worked example).

**Q: What breaks BM25 across shards?** IDF/avgdl are global statistics; per-shard local stats
make scores incomparable, so you must share global term statistics or accept the
approximation.

**Q: BM25's fundamental limitation?** It's lexical — no synonymy or semantics; "leader
election" won't match "consensus" unless the words appear. Hybrid semantic ranking fixes it.
